## Independent oracle and a rejected candidate

The oracle is the actual MySQL 8.0.45 aarch64 server from official image
`mysql@sha256:4af1f8815716546f5b12410f7621f37f93db8dd11a184706ef59111930b8c2ff`.
The task-owned container has no network and no published ports. SQL specifies
collations explicitly. A reproducible generator and compressed native answers
are in `pkg/common/collation/testdata/`; expected answers are not generated by
MO's implementation.

- 205 input strings, all 42,025 ordered pairs per collation, including ASCII
  controls/NUL, empty/padded strings, case/accent variants, combining sequences,
  punctuation, Chinese and supplementary characters.
- 65,536 character samples: all valid BMP code points (excluding surrogates),
  plus 2,048 supplementary samples. Each sample's native general-ci and binary
  `WEIGHT_STRING` output was verified against the selected mappings.
- `utf8mb4_bin` and `utf8mb4_general_ci`: 84,050 comparison results, no mismatch
  for the selected compact PAD-aware key.
- Real `utf8mb4_0900_ai_ci` results are retained separately. MO's current alias
  for that name is general-ci; these are not interchangeable semantics and this
  change does not add native UCA 9.0 support.

The previous trim-then-compare candidate disagreed on 362 general-ci pairs and
318 text `_bin` pairs. Example: MySQL compares the empty string greater than
NUL under these PAD SPACE collations, because the implicit SPACE weight is
larger than NUL. A shorter byte string instead sorts before any extension.
The existing aggregate comparator has that trim/length behavior; extracting its
weight table does not silently change that comparator in this implementation.
Scalar, aggregate and hash-domain alignment is still a feature blocker before
index activation, not a waived discrepancy.

The mapping table itself agreed for every sampled character. Reuse its existing
TiDB lineage and license attribution in one owner (`pkg/common/collation`).
There is no need for a second weight table, process-global locale or CGo call
for each transformed value.

## Normative bytes

The following is the format of the weight payload **before** unchanged tuple
string framing. Domain and format are supplied by schema/plan metadata; neither
is embedded in each key. This format covers the existing PAD SPACE general-ci
and UTF8MB4Bin classes. Actual binary/legacy values bypass transformation.

1. Obtain each character's collation weight. General-ci contributes one mapped
   weight per character; text `_bin` uses the Unicode scalar value.
2. Defer weights equal to SPACE (32). Discard a deferred run at end of input.
3. For an interior SPACE run, emit one `21` byte per SPACE if the next non-SPACE
   weight is below 32, or one `23` byte per SPACE if that weight is above 32.
4. Encode a non-SPACE weight `w`:
   - `0 <= w < 32`: one byte `w + 1` (`01` through `20`).
   - `33 <= w < 128`: one byte `w + 3` (`24` through `82`).
   - `w >= 128`: canonical UTF-8 encoding of the weight scalar.
5. End the payload with `22`.

All numbers above are hexadecimal when shown as two-digit byte strings. The
payload has no zero bytes. UTF-8 is used here as an order-preserving integer
encoding; the complete payload is opaque binary, not necessarily valid UTF-8.

| Original, general-ci | Payload hex | Complete tuple field hex |
| --- | --- | --- |
| empty or SPACE | `22` | `46012200` |
| NUL | `0122` | `4601012200` |
| `a` / `A ` | `4422` | `4601442200` |
| `a` SPACE NUL | `44210122` | `46014421012200` |
| `a b` | `44234522` | `46014423452200` |
| `Alpha` / `alpha ` | `444f534b4422` | `4601444f534b442200` |

Tuple framing is the existing `46 01 <escaped payload> 00`. Because generated
payloads contain no zero, new weight keys add no zero-escape expansion. Numeric,
NULL and other tuple parts retain their existing encodings. An ordinary ASCII
payload occupies the trimmed input length plus one byte. General-ci can change
Unicode encoded lengths; a conservative bound is four bytes per input byte
plus one, without declared-column-width padding. Storage-specific maximum key
sizes remain enforced by their owners; no output is truncated to meet a limit.

### Why this preserves order

Non-SPACE weights retain their numeric order. In the new alphabet:

`low weight < low-side SPACE < end/PAD < high-side SPACE < high weight`.

When one source ends first, its implicit SPACE suffix compares on the correct
side of the other source's first remaining non-SPACE weight. If both sources
have SPACE runs, their side markers resolve opposite-side cases; within one side,
comparing a SPACE marker with the following actual weight orders different run
lengths correctly. Removing only trailing SPACE leaves one canonical identity
for every equivalent value. It does not append original spelling or length.

The property test enumerates all 781 words of length 0-4 over weights
`{0,31,32,33,65535}` and checks 609,961 pairs against a separate comparator that
explicitly pads the shorter word with SPACE. Native MySQL is a second independent
oracle. Tuple tests add numeric parts before/after the text field and check
that escaping and field boundaries preserve the payload order.

## Admission, ownership and decoding

- `LegacyKeyFormat=0` preserves raw persisted bytes, even for a column that
  already has nonbinary collation metadata. `PADSpaceKeyV1=1` is an explicit
  caller-selected format. These Go constants are not yet a catalog migration.
- New transformed keys reject malformed UTF-8 and unknown domains. Legacy and
  actual binary paths accept and preserve arbitrary bytes. Existing malformed
  aggregate comparison behavior remains intact. Any future rebuild encountering
  malformed text must fail before publication; it cannot silently replace bytes.
- `StringKeyPart` resolves the domain once. Raw keys borrow original bytes with
  no weight allocation. Transformed keys borrow caller scratch until reused;
  scratch and source must be disjoint. Vector result append copies the bytes.
- Tuple encoding checks fixed-buffer capacity before appending a field, so a
  failure cannot leave a partial new field. New decoding checks type framing,
  escapes, termination and canonical weight grammar and returns owned bytes.
- Decoding returns `Opaque=true` for weights. It cannot recover original text.
  Original values must come from main-row columns; legacy generic `serial` and
  `serial_extract` are not redefined to pretend otherwise.

## Executable query integration and its exact limit

`MakeCollationKeyExpr` binds `internal_collation_key(original, schema_charset)`.
The second argument is a constant in the plan, not per-key stored metadata.
Both tuple producers and that vector function use the same resolved key-part
implementation. The expression has a MORPC v68 sender/receiver fence using the existing
remote-expression capability walk. Missing/older protocol versions are rejected,
including a downgrade between sending and decoding. This is an expression
transport fence, not a durable-table activation mechanism.

The return type is binary and can be passed to unchanged
`serial`/`serial_full`. No cast to indexed column width is performed on probes.

Tests execute the expression with real vectors, constants, NULLs, selection
masks and invalid input. They marshal/unmarshal the plan, execute
`serial(42, internal_collation_key(...))`, and compare the output to the physical
tuple encoder, including over-width lookup values. Reapplying the helper to an
existing same-domain key expression is a no-op. Unproven binary provenance is
rejected rather than transformed again.

This proves the expression/tuple boundary, **not** that PK/UNIQUE/secondary index
plans already select it. No ordinary table's writer or optimizer has been
switched. The following are still mandatory before that switch:

1. Durable per-relation/index format transport, and a concrete homogeneous
   upgrade admission check. Old nodes ignoring a property must not write raw
   bytes into a weight-key index.
2. Hidden physical string PK, every index/DML writer, duplicate probe, lock
   identity and DDL backfill/precheck must construct the same key. Schema copy,
   recovery and rebuild must carry the chosen format.
3. Every lookup, IN/range/join/runtime filter and covering-index substitution
   must respect the stored format and original-value recoverability. Existing
   scalar/group/hash/MIN/MAX semantics must agree before optimized activation.
4. Real persisted-object ZM/Bloom/seek tests, transaction failures and restart
   tests; a vector-expression PASS is not evidence that storage pruning ran.

The first production activation therefore remains blocked on these concrete
closure items. This document freezes the D1 payload and records the working
D2/query-expression boundary without claiming D3-D5 or issue completion.

## Validation record (local, 2026-09-14)

- Native generator rerun reproduced the 126,075 comparison answers and 65,536
  mapping pairs. Only the two supported PAD SPACE domains count as compatibility
  acceptance; native 0900 is the explicit semantic control.
- Shared codec unit/property/golden tests PASS. A bounded fuzz run completed
  174,704 executions without failure; tuple decoding fuzz completed 33,704
  executions. These are not exhaustive malformed-input proofs.
- `pkg/container/types` full tests PASS; `pkg/sql/plan/function` full tests PASS
  after fixing the new function's stable-ID registration.
- Focused planner expression transport, remote sender/receiver compatibility,
  existing serial and aggregate comparison regression groups PASS.
- Existing ZM/Bloom primitives accepted transformed equivalent probes after
  summary/filter serialization, including long-key truncation. A deliberately
  untransformed probe produced the expected ZM false negative. This is filter
  primitive coverage, not evidence of real object/block query pruning.
- All measured preallocated key microbenchmarks report zero allocations. Raw
  mode borrows the source bytes. Microbenchmark CPU numbers are local evidence,
  not a database throughput or end-to-end index performance claim.

Raw logs, pinned image identity, SQL/results and local diff evidence live in the
ignored `artifacts/issue-28164-d1/` directory. Public PK/UNIQUE/secondary-index BVT,
real persisted-object pruning, migration/recovery and multi-CN acceptance have
not run. No production-enable or full-issue PASS is implied.
